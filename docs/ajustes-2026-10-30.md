# Ajustes del 2026-10-30: auditoría del sistema y seguridad del acceso

Por seguridad, cada operación queda registrada con quién la hizo, cuándo, desde dónde y con qué resultado, para poder
rastrear un acceso indebido. La auditoría **solo se guarda en la base de datos**: no tiene pantalla ni endpoint, así que
no se puede consultar ni alterar desde la aplicación; se revisa directamente en la base.

## 1. Qué se registra
`AuditoriaFilter` (en la cadena de seguridad, después del filtro JWT) registra al terminar cada petición:
- toda operación que modifica datos (`POST`, `PUT`, `PATCH`, `DELETE` en `/api/v1/sgtg/...`);
- las descargas de documentos (`GET /trabajos-grado/{id}/archivos`);
- los inicios de sesión, exitosos o fallidos, con el correo intentado (nunca la contraseña).

Las demás consultas no se registran, para no llenar la tabla de ruido. Si el registro falla, la petición no falla (se
escribe el error en el log).

## 2. Tabla `auditoria`
| Columna | Contenido |
|---|---|
| `fecha` | Fecha y hora real del servidor en Bogotá (no el reloj ajustable de desarrollo) |
| `usuario_id`, `usuario`, `roles` | Usuario autenticado y sus roles en ese momento; en un inicio de sesión fallido, el correo intentado |
| `sesion` | Sesión con la que se hizo (identificador `jti` del token, ver §6): une todas las acciones de un mismo inicio de sesión |
| `ip`, `agente_usuario` | IP del cliente y navegador / sistema operativo |
| `metodo`, `ruta` | Método HTTP y ruta con sus parámetros |
| `operacion` | Operación que la atendió, ej. `TrabajoGradoController.agendarReunion` |
| `trabajo_id`, `parametros` | Trabajo de grado afectado y variables de la ruta (ej. `numero=2, trabajoId=7`) |
| `estado_http`, `resultado` | Código de respuesta y `EXITOSA`, `NO_AUTENTICADO`, `SIN_PERMISO`, `RECHAZADA` o `ERROR` |

La entidad es `@Immutable` (Hibernate nunca la actualiza) y `AuditoriaRepository` solo tiene `save`: no hay métodos
para consultar, modificar ni borrar registros. Cada registro se guarda en su propia transacción.

Ejemplos de consulta directa:
```sql
-- Intentos de inicio de sesión fallidos por IP en el último día
SELECT ip, usuario, COUNT(*) FROM auditoria
WHERE operacion = 'AuthController.login' AND resultado <> 'EXITOSA' AND fecha > NOW() - INTERVAL 1 DAY
GROUP BY ip, usuario ORDER BY 3 DESC;
-- Todo lo que hizo un usuario
SELECT fecha, ip, metodo, ruta, resultado FROM auditoria WHERE usuario = 'correo@unicauca.edu.co' ORDER BY fecha;
-- Todo lo que se hizo en una sesión, desde su inicio hasta su cierre
SELECT fecha, ip, operacion, ruta, resultado FROM auditoria WHERE sesion = '<jti>' ORDER BY fecha;
-- Intentos de usar una sesión ya cerrada (posible token robado)
SELECT fecha, sesion, ip, ruta FROM auditoria WHERE sesion IS NOT NULL AND usuario IS NULL;
```

## 3. IP real del cliente
Nginx envía `X-Forwarded-For`; con `server.forward-headers-strategy=native` (configurable con `SGTG_FORWARD_HEADERS`)
el backend toma de ahí la IP del cliente. Quien llegue directo al puerto del backend podría falsear esa cabecera: en
producción el puerto 8080 no debe exponerse (en `docker-compose` está abierto solo para pruebas con Thunder Client).

## 4. Recomendaciones para producción (base de datos)
- Que el usuario con el que se conecta la aplicación solo pueda insertar en la auditoría, no modificarla ni borrarla:
  ```sql
  REVOKE UPDATE, DELETE ON sgtg.auditoria FROM 'usuario_app'@'%';
  GRANT SELECT, INSERT ON sgtg.auditoria TO 'usuario_app'@'%';
  ```
  (con `ddl-auto=update` el usuario necesita además permisos de esquema; en producción conviene `ddl-auto=validate`).
- Definir cuánto tiempo se conservan los registros; el borrado de los antiguos lo hace el administrador de la base de
  datos, nunca la aplicación.

## 5. Borrados que siguen existiendo
Los trabajos de grado, los usuarios y las solicitudes no se borran (se anulan, cancelan o inactivan). Aún borran: las
notificaciones (cada usuario en su bandeja), los días no hábiles del calendario (administrador), los archivos de una
operación que falló (el sistema) y el reinicio del reloj de desarrollo. Todos quedan en la auditoría.

## 6. Sesiones: identificador y cierre
- **Identificador de sesión.** Cada token lleva un identificador único (`jti`) que queda en la columna `sesion` de la
  auditoría:
  - En el inicio de sesión exitoso lo pone `AuthController`.
  - En las demás peticiones lo pone `JwtAuthenticationFilter`, aunque la sesión esté cerrada o el usuario inactivo. Así
    se ve si alguien usa un token que ya no debería servir.
- **`POST /api/v1/sgtg/auth/logout`** (con el token en `Authorization`):
  - Cierra esa sesión: el token deja de ser aceptado aunque no haya vencido, y las demás sesiones del usuario siguen.
  - Responde 204 aunque no haya token o ya no sirva.
  - El front lo llama al cerrar sesión y agrega `?motivo=inactividad` cuando cierra por inactividad (30 minutos). El
    motivo queda en la ruta de la auditoría.
- **Tabla `sesiones_cerradas`** (`sesion`, `expira`): guarda cada sesión hasta que vence su token; después ya no hace
  falta recordarla.

## 7. Bloqueo por intentos fallidos
- **En el backend, por correo** (`IntentosAcceso`, tabla `intentos_acceso`):
  - Tras 5 fallos seguidos, sin pasar más de 15 minutos entre uno y otro, el correo queda bloqueado 15 minutos.
  - Durante el bloqueo se responde 401 con "Demasiados intentos fallidos…" sin revisar la contraseña, aunque sea la
    correcta.
  - Se lleva por correo, en minúsculas, exista o no la cuenta. Así el bloqueo tampoco revela qué correos están
    registrados.
  - Un inicio de sesión exitoso borra los fallos. El bloqueo usa el reloj real, no el ajustable.
- **En Nginx, por IP:**
  - Hasta 20 inicios de sesión por minuto, con ráfagas de 20. Pasado eso responde 429 y el front muestra "Demasiados
    intentos…".
  - Frena a quien prueba muchos correos desde el mismo equipo.
  - Esas peticiones no llegan al backend, así que no quedan en la tabla de auditoría, solo en el log de Nginx
    (`docker compose logs web`).
- **Respuestas que ya no revelan datos** (ya estaba así antes de estos ajustes):
  - Un correo inexistente y una contraseña incorrecta responden igual y tardan lo mismo.
  - "Cuenta inhabilitada" solo se muestra con la contraseña correcta.

## 8. Limpieza programada
`LimpiezaAccesosScheduler` (todos los días a las 03:00, `sgtg.limpieza-accesos.cron`) borra:
- los intentos fallidos de hace más de un día;
- las sesiones cerradas cuyos tokens ya vencieron.

La auditoría no se toca.

## 9. Otros cambios
- **Se eliminaron los endpoints de prueba** `GET /auth/` y `GET /test/`, que respondían "Hello, World!".
- **El correo del login se limita a 255 caracteres.**
- **Validaciones que ya estaban cubiertas:**
  - Los archivos solo se aceptan si su contenido empieza con la firma `%PDF-`, no basta con la extensión.
  - Las descargas no pueden salir de la carpeta de archivos.
- **Cabeceras de seguridad, límite por IP y cierre por inactividad:** están en el front (`nginx.conf`,
  `nginx-cabeceras-seguridad.conf`, `SessionInactivityService`). Las respuestas de la API ya traían las de Spring
  Security (`X-Content-Type-Options`, `X-Frame-Options`, `Cache-Control`).
